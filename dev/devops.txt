@module Linux: finding your way around
DevOps work happens in a terminal, usually on a Linux server with no desktop. These labs use your Arch laptop.

**Before you start:** read a command before you run it, especially with `sudo` or `rm`. There is no bin in the terminal. Do experiments in a folder like `~/lab`.

Everything is a file in one tree that starts at `/`.

- `/etc`: system settings
- `/home`: your files
- `/var/log`: logs
- `/usr`: installed programs
- `/tmp`: temporary files

```bash
pwd                  # where am I
ls -la               # list everything, with details
cd ~/lab             # move
mkdir -p a/b         # make folders
cp x y; mv x y       # copy, move or rename
rm file              # delete, no undo
cat f; less f        # read a file
man ls               # the manual
```

**Paths:** an absolute path starts at `/`. A relative path starts from where you are. `.` is here, `..` is one level up, `~` is your home.

**Permissions:** `ls -l` shows something like `-rwxr-x---`. That is three groups: owner, group, everyone else. r = read, w = write, x = run. As numbers: r=4, w=2, x=1, so `chmod 750 f` means rwx, r-x, nothing.

```bash
chmod +x script.sh
sudo chown kristian file
```

`sudo` runs one command as root, the all-powerful user. Use it only when needed.

@module Text, pipes and search
Linux tools do one small job each. A **pipe** `|` sends one program's output into the next.

```bash
cat log | grep ERROR | wc -l
```

Redirection:

```bash
cmd > file      # write output to a file, replacing it
cmd >> file     # add to the end
cmd 2> err      # errors only
cmd > all 2>&1  # both
```

The tools you will use daily:

- `grep -i word f`: find lines
- `sort`, `uniq -c`: order and count
- `head -5`, `tail -f`: start of a file, or follow it live
- `cut -d, -f2`: pick a column
- `sed 's/a/b/g'`: replace text
- `awk '{print $1}'`: pick fields
- `find . -name '*.log'`: find files
- `du -sh *`: what is using the space
- `journalctl -u name`: logs of a service

The classic question "which IP hits us most?" takes one line:

```bash
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head
```

@module Processes and services
A running program is a **process**, with an id (PID).

```bash
ps aux | grep name
top          # live view; htop is nicer
kill PID     # ask it to stop
kill -9 PID  # force it
cmd &        # run in the background
```

**systemd** starts and looks after services on most Linux servers, Arch included.

```bash
systemctl status sshd
sudo systemctl start sshd
sudo systemctl enable sshd    # start at boot
journalctl -u sshd -f         # follow its log
```

A service is described by a **unit file**:

```ini
[Unit]
Description=My app
After=network.target

[Service]
ExecStart=/home/kristian/lab/app.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Put it in `/etc/systemd/system/app.service`, then run `sudo systemctl daemon-reload`.

A **timer** runs something on a schedule. It is the modern version of cron.

@module Bash scripting
A script is commands in a file. Anything you do twice can become one.

```bash
#!/usr/bin/env bash
set -euo pipefail          # stop on errors, unset variables, failed pipes

name="${1:-world}"         # first argument, with a default
echo "hello $name"

if [[ -f "$name" ]]; then
    echo "file exists"
fi

for f in *.log; do
    echo "$f"
done

count=$(wc -l < file.txt)  # save a command's output
```

Rules that prevent most bugs:

- Quote variables: `"$x"`, or a name with a space splits in two.
- Start with `set -euo pipefail`.
- Every command returns an **exit code**. 0 means success. `$?` holds the last one.
- `shellcheck script.sh` finds mistakes for you. Install it.

Functions:

```bash
log() { echo "$(date +%T) $*"; }
```

@module Git
Git stores snapshots of your project. Every DevOps pipeline starts from it.

```bash
git status; git diff
git add file; git commit -m "Say what changed"
git log --oneline --graph
git switch -c feature      # new branch
git switch main
git merge feature
git pull; git push
```

Three areas: **working folder**, **staging area** (`git add`), **history** (`git commit`).

Fixing mistakes:

```bash
git restore file           # throw away local changes
git restore --staged file  # unstage
git commit --amend         # fix the last commit
git revert HASH            # new commit that undoes one
git reset --hard HASH      # dangerous: drops work
git reflog                 # find "lost" commits
```

`.gitignore` lists files Git should skip. **Never commit secrets.** Once pushed, treat a password as leaked and change it. Removing it later does not remove it from history.

A **merge conflict** is Git asking you to choose. Open the file, keep what is right, delete the markers, `git add`, commit.

Teams use **pull requests**: work on a branch, open a PR, get a review, merge.

@module Networking
Most production problems end up here. Learn to test each layer in order.

- **IP address**: where a machine is. `192.168.x.x`, `10.x.x.x` and `100.x.x.x` (Tailscale) are private ranges.
- **Port**: which program on that machine. 22 SSH, 80 HTTP, 443 HTTPS, 5432 Postgres.
- **DNS**: turns a name into an IP.
- **TCP**: a reliable connection. **UDP**: fast with no guarantee.
- **HTTP**: requests and responses on top of TCP. **TLS** makes it HTTPS.
- **Firewall**: decides which ports are reachable.

Debugging order: name, machine, port, app.

```bash
ip a                     # my addresses
ip route                 # my gateway
ping host                # is the machine there
dig example.com          # DNS
ss -tlnp                 # which ports are listening here
curl -v https://site     # the full HTTP exchange
traceroute host          # the path
```

Status codes: 2xx fine, 3xx redirect, 4xx your request is wrong, 5xx the server failed. 502 and 504 usually mean a proxy cannot reach the app behind it.

A server listening on `127.0.0.1` is reachable only from that machine. `0.0.0.0` means every network, so be careful with it.

@module SSH and remote machines
SSH gives you a secure terminal on another machine. It is how you reach servers.

```bash
ssh user@host
ssh-keygen -t ed25519     # make a key pair
ssh-copy-id user@host     # install your public key
scp file user@host:/tmp/
rsync -av folder/ user@host:folder/
```

A **key pair** has two parts. The private key stays on your machine and is never shared. The public key goes on the server.

`~/.ssh/config` saves typing:

```
Host pc
    HostName 100.x.x.x
    User kristian
```

Harden a server in `/etc/ssh/sshd_config`: `PasswordAuthentication no` and `PermitRootLogin no`. Keep your current session open while you test, or you can lock yourself out.

**Port forwarding** reaches a service through SSH:

```bash
ssh -L 8080:localhost:80 user@host
```

@module Docker
A **container** is a process with its own files and network, sharing the host's kernel. It starts in moments and behaves the same on every machine. That ends "it works on my laptop".

- **Image**: a read-only template.
- **Container**: a running copy of an image.
- **Dockerfile**: the recipe for an image.

```bash
sudo pacman -S docker
sudo systemctl enable --now docker
docker run --rm hello-world
docker ps -a; docker images; docker logs NAME
docker exec -it NAME sh
```

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
USER nobody
EXPOSE 8000
CMD ["python", "app.py"]
```

Each line is a cached **layer**. Copy files that change rarely first, so builds stay fast. Use `.dockerignore`. Small base images have fewer security holes. Do not run as root.

```bash
docker build -t myapp .
docker run -d -p 8000:8000 --name web myapp
```

`-p 8000:8000` connects a host port to a container port. Container files disappear with the container, so keep data in a **volume**: `-v data:/var/lib/data`.

Adding yourself to the `docker` group is the same as giving yourself root, so know what it means.

@module Docker Compose
Real apps have several parts. **Compose** describes them all in one file.

```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
volumes:
  dbdata:
```

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f web
docker compose down       # add -v to delete the data too
```

Containers reach each other by service name: `db` above. Secrets go in a `.env` file, which stays out of Git.

@module CI/CD
**CI** (continuous integration): every push is built and tested automatically. **CD** (continuous delivery): what passes is shipped automatically. The aim is small, boring, frequent releases.

A typical pipeline: checkout, install, lint, test, build, deploy.

GitHub Actions reads `.github/workflows/*.yml`:

```yaml
name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: pytest
```

Terms: a **workflow** holds **jobs**, jobs hold **steps**, and each job runs on a fresh machine called a **runner**.

Secrets go in the repo's settings and are read with `${{ secrets.NAME }}`. Never print them. Give a deploy token the least power it needs.

If the main branch can break, turn on branch protection so tests must pass before a merge.

Check GitHub's docs for the current version numbers of the actions.

@module Cloud basics
"The cloud" is someone else's computers, rented by the minute and controlled by an API.

- **IaaS**: you rent virtual machines. You manage everything above the hardware. AWS EC2.
- **PaaS and serverless**: you give it code. Cloudflare Workers, AWS Lambda. Your apps already run this way.
- **SaaS**: you use the finished product.

Every big cloud has the same core pieces under different names:

- Compute: EC2, Workers, Lambda
- Storage: S3, Cloudflare R2
- Database: RDS, D1
- Network: VPC, load balancers
- Identity: IAM

**Identity** is the first thing to learn. Give each person and program the least permission that works.

**Scaling:** vertical means a bigger machine. Horizontal means more machines behind a load balancer, which needs apps that keep no state on themselves.

**Reliability:** run in more than one zone. Keep backups, and test restoring them. A backup you never restored is only a hope.

**Cost:** forgotten resources keep charging. If you ever put a card on an account, set a budget alert first, and delete what you stop using. Cloudflare's free tier avoids this.

@module Infrastructure as code
Clicking in dashboards cannot be reviewed, repeated or undone. **Infrastructure as code** describes servers and settings in files kept in Git.

Terraform (or OpenTofu, its open source twin with the same language) declares what should exist. You do not write steps.

```hcl
terraform {
  required_providers {
    local = { source = "hashicorp/local" }
  }
}

resource "local_file" "hello" {
  filename = "${path.module}/hello.txt"
  content  = "hello"
}
```

```bash
terraform init
terraform plan     # what would change
terraform apply
terraform destroy
```

The **state** file records what Terraform manages. It can contain secrets, so keep it out of Git. Teams store it remotely.

**Read the plan** every time. A line starting with `-/+` means something will be deleted and rebuilt.

**Ansible** is the other half: it logs in over SSH and configures machines, using YAML. Terraform creates things, Ansible sets them up.

On Arch, check with `pacman -Ss terraform` and `pacman -Ss opentofu`. For OpenTofu the command is `tofu`.

@module Kubernetes
Docker runs containers on one machine. **Kubernetes** runs them across many, restarts failures, and rolls out updates. You declare what you want, and it keeps making that true.

- **Pod**: one or more containers together. The smallest unit.
- **Deployment**: keeps N copies of a Pod and handles updates.
- **Service**: a stable address in front of Pods.
- **Ingress**: lets outside traffic in.
- **ConfigMap, Secret**: settings for Pods.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
```

```bash
minikube start
kubectl apply -f web.yaml
kubectl get pods
kubectl describe pod NAME    # read Events at the bottom when stuck
kubectl logs NAME
kubectl rollout undo deployment/web
```

You may never need it for small apps, but most DevOps jobs ask for it.

@module Monitoring and incidents
You cannot fix what you cannot see.

- **Logs**: what happened.
- **Metrics**: numbers over time, such as CPU, errors, response time.
- **Traces**: one request's path through many services.

Watch the four golden signals: **latency, traffic, errors, saturation**.

Common tools: **Prometheus** collects metrics, **Grafana** draws them, **Alertmanager** sends alerts. An alert should mean a person must act. Noisy alerts get ignored.

When something breaks:

- Stop the damage first: roll back before you investigate.
- Write down what you see and when.
- Change one thing at a time.
- Afterwards, write a **postmortem**: what happened, why, what stops it happening again. Blame the system, not the person.

**Backups:** keep 3 copies, on 2 kinds of storage, with 1 off-site. Test restoring.

**Security basics:** update software, keep few open ports, use keys over passwords, store secrets outside code, and give least privilege.

With Compose, run Prometheus, Grafana and `node-exporter`. Build a dashboard of your laptop's CPU, memory and disk.

Done when the dashboard shows live numbers.
@hint
`prom/prometheus`, `grafana/grafana`, `prom/node-exporter`, `prometheus.yml`

@task lab 2 Uptime alert
Use your health check script on a systemd timer. Make it send you a notification when a site fails.

Done when a fake failing URL reaches your phone. A free service like ntfy works with `curl`.
@hint
`ntfy.sh`, `curl -d`, keep your topic name private

@task lab 2 Backup and real restore
Back up the database from your Compose app with a script, delete the data, and restore it.

Done when the app works again, and you timed the restore.
@hint
`pg_dump`, `psql`, `docker compose exec -T`

@task lab 3 Break it, then write a postmortem
Stop the database in your Compose app with no warning, and fill the app's logs with errors. Find the cause using only logs and metrics. Then write a one-page postmortem.

Done when the postmortem has a timeline, the cause, and two changes you would make.
@hint
`docker compose logs`, `docker stats`, Grafana

@module Final project: ship it for real
Put everything together, with no steps given. This is what you can show on a CV or in an interview, so make the repo public and keep secrets out.

The goal: one small app of your own idea, with a database, built and shipped like a professional team would do it.

Write the README last, with a diagram of how it all fits together. In an interview you will be asked why you chose each part, so keep notes on your decisions.

@task lab 2 Plan and containerise
Choose the app. Write a short plan: parts, ports, data, risks. Build it with Docker and Compose.

Done when a stranger could run it with one command from your README.
@hint
`docker compose up`, `.env.example`

@task lab 3 Pipeline
Add tests, a linter and an image build, running on every pull request. Use protected main.

Done when bad code cannot reach main.
@hint
GitHub Actions, branch rules, GHCR

@task lab 3 Deploy with no hands
Make a merge to main update the running app on your laptop over Tailscale, or on Cloudflare. It must be able to roll back.

Done when a merge goes live with no manual step, and you have done one rollback.
@hint
GitHub Actions, a self-hosted runner or Tailscale action, image tags as versions

@task lab 3 Run it like production
Add monitoring, an alert, automatic backups and a tested restore. Write a short runbook: how to restart, roll back and restore.

Done when someone else could keep it running using only your runbook.
@hint
Prometheus, Grafana, systemd timers, `pg_dump`

@task lab 3 Show it
Publish the repo with the README, diagram, screenshots and what you would do next. Check the history for secrets first.

Done when you can explain the whole system out loud in 5 minutes.
@hint
`git log -p | grep -i`, `gitleaks`
